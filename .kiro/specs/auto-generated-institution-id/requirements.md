# Requirements Document

## Introduction

This feature is an architectural refactor of the multi-tenant identity model used by the
application (an Electron + Firebase school-management system). Today, the user-entered
"Massar code" (رمز مسار, matching the regex `^\d+[A-Za-z]{1,2}$`) is used directly as the
technical tenant key `schoolId`. The same value simultaneously serves as the Firestore
partition key (`schools/{schoolId}`), the Firebase auth custom claim `schoolId`, the local
`sync_config.school_id`, and `institution_config.code_etablissement`, and as the sync key in
the sync engine.

Using a mutable, business-meaningful, user-entered value as the surrogate tenant key
violates multi-tenant design best practice and is the sole reason a complex
"identity-change" approval mechanism exists (request → admin approval → apply).

The chosen solution is a hybrid model:

- `schoolId` becomes an auto-generated surrogate key. The Cloud Function
  `bootstrapInstitution` generates it server-side (unique, immutable, opaque) using a
  collision-check-and-retry loop against the existing `schools/{schoolId}` existence check.
- `massarCode` becomes a separate descriptive field used for display in reports, search,
  and re-linking, and is freely editable.

The refactor must preserve correct operation for institutions that were already configured
under the old model (their existing `schoolId` must keep working). Cloud Function changes
take effect only after the user runs `firebase deploy`; the application must behave
predictably both before and after deployment.

## Glossary

- **System**: The overall application, comprising the Electron desktop client, the local
  SQLite database, and the Firebase backend (Firestore, Auth, Cloud Functions).
- **Bootstrap_Function**: The Cloud Function `bootstrapInstitution` in
  `firebase/functions/index.js` that provisions a new institution, its first admin user, and
  its Firestore documents.
- **Setup_Client**: The Electron client setup flow, comprising `setup.html`,
  `js/pages/setup.js`, and the IPC handler in `main/ipc/institution.js`.
- **Institution_IPC**: The IPC handler module `main/ipc/institution.js`, including the
  `institution:setup-new`, `institution:relink`, and `institution:get-status` channels.
- **School_Id**: The technical surrogate tenant key. After this feature, an opaque,
  auto-generated, immutable string used as the Firestore partition key (`schools/{School_Id}`),
  the Firebase auth custom claim `schoolId`, the local `sync_config.school_id`, and the sync
  key in the sync engine.
- **Massar_Code**: A descriptive, user-editable institution identifier (رمز مسار). After
  this feature, THE System SHALL treat it as ordinary descriptive institution information,
  handled the same way as the institution name or any other descriptive field — editable
  directly, with no approval workflow — subject only to a character-set constraint: uppercase
  letters (A-Z) and digits (0-9), matching the pattern `^[A-Z0-9]+$`, with a maximum length of
  20 characters. It is used for display, search, and re-linking but never as the tenant key.
  The Massar_Code is the only institution identifier a user ever enters or sees: once at
  initial setup (Setup_Client) and, afterward, on the institution-information screen
  (`settings-school.html`) where a principal may view and directly edit it. The School_Id, by
  contrast, is never entered or displayed anywhere.
- **Legacy_Institution**: An institution that was configured before this feature, whose
  `School_Id` equals its `Massar_Code`.
- **Identity_Change_Mechanism**: The existing request/approval/apply flow
  (`institution:submitIdentityChangeRequest`, `institution:applyApprovedIdentityChange`, and
  the Cloud Functions `submitInstitutionIdentityChangeRequest` and
  `getInstitutionIdentityChangeRequestsForSchool`) that exists only because `School_Id` was
  previously mutable.
- **Relink_Operation**: The `institution:relink` IPC operation that links a device to an
  existing institution.
- **Setup_Completed**: The persisted local state indicating the institution has finished
  initial configuration on the device (`institution_config.setup_completed`).

## Requirements

### Requirement 1: Server-side generation of the surrogate School_Id

**User Story:** As a system architect, I want the technical tenant key generated by the
server, so that the tenant key is opaque and decoupled from any user-entered value.

#### Acceptance Criteria

1. WHEN the Bootstrap_Function receives an institution-creation request that contains all required institution fields, THE Bootstrap_Function SHALL generate the School_Id server-side and SHALL NOT use any client-supplied identifier value as the School_Id.
2. WHERE the institution-creation request body contains a `schoolId` value, THE Bootstrap_Function SHALL ignore the supplied `schoolId` value and use the server-generated School_Id.
3. THE Bootstrap_Function SHALL generate a School_Id consisting of 20 to 30 randomly assigned characters, using only the digits 0-9 and uppercase letters A-Z, that contains no substring derived from the Massar_Code or any other user-entered value. Restricting the character set to uppercase-only avoids case-normalization steps elsewhere in the System silently mutating the value.
4. WHEN the Bootstrap_Function generates a School_Id, THE Bootstrap_Function SHALL persist the institution document at `schools/{School_Id}` with the generated School_Id.
5. WHEN the Bootstrap_Function creates the first admin user, THE Bootstrap_Function SHALL set the Firebase auth custom claim `schoolId` to the generated School_Id.
6. IF the institution-creation request omits any required institution field, THEN THE Bootstrap_Function SHALL reject the request, SHALL return an error response identifying the missing field, and SHALL NOT create any institution document or admin user.

### Requirement 2: Uniqueness of the generated School_Id

**User Story:** As a system architect, I want each generated tenant key to be unique, so that no two institutions share a Firestore partition.

#### Acceptance Criteria

1. WHEN the Bootstrap_Function generates a candidate School_Id, THE Bootstrap_Function SHALL determine whether a document already exists at `schools/{candidate}` before using the candidate. This first candidate check counts as generation attempt 1 of 5.
2. IF a candidate School_Id already exists at `schools/{candidate}` and fewer than 5 generation attempts have been made so far, THEN THE Bootstrap_Function SHALL generate a new candidate, counting it as the next attempt, and repeat the existence check.
3. IF 5 generation attempts have been made and every one of those 5 candidates collided with an existing document, THEN THE Bootstrap_Function SHALL return an error response with an identifying error code and SHALL NOT create any institution document. THE Bootstrap_Function SHALL NOT make more than 5 total generation attempts (the initial attempt plus at most 4 retries).
4. WHEN the Bootstrap_Function confirms a candidate School_Id has no existing document, THE Bootstrap_Function SHALL use that candidate as the School_Id for the new institution.
5. WHEN the Bootstrap_Function selects a confirmed candidate, THE Bootstrap_Function SHALL create the institution document for that candidate so the School_Id cannot be claimed by a concurrent request.

### Requirement 3: Immutability of the School_Id

**User Story:** As a system architect, I want the tenant key to be immutable after creation, so that data partitioning and auth claims remain stable for the lifetime of the institution.

#### Acceptance Criteria

1. WHEN an institution record is created with a School_Id, THE System SHALL retain that School_Id, unchanged in value, as the Firestore partition key from the moment of creation until the institution record is deleted.
2. WHEN a user edits any field of an institution record other than School_Id, including the Massar_Code, THE System SHALL persist the edited fields while retaining the existing School_Id with its exact original value.
3. THE System SHALL exclude School_Id from the set of fields editable through any user interface, and THE System SHALL NOT display the School_Id value to any end user through any screen, form, settings panel, sync-configuration panel, diagnostic message, or connection-test result — the Massar_Code is the only institution identifier ever shown to or enterable by a user, both at initial setup and afterward through the institution-information screen.
4. IF any operation, through a user interface, an API call, or a direct write request, attempts to modify the School_Id of an existing institution record, THEN THE System SHALL reject the modification, SHALL retain the original School_Id value with no change, and SHALL return an error response indicating that the School_Id is immutable.
5. THE System SHALL treat any existing settings or sync-configuration input field that currently reads or writes the raw School_Id (such as an administrator-facing sync-configuration form) as a defect to be corrected under this feature: such a field SHALL be removed from user-facing display, and submitting that form SHALL NOT alter the stored School_Id under any circumstance.

### Requirement 4: Client adoption of the server-generated School_Id

**User Story:** As a device owner setting up a new institution, I want the client to store the identifier the server created, so that local data and sync use the correct tenant key.

#### Acceptance Criteria

1. WHEN the Setup_Client receives a Bootstrap_Function response that indicates success and contains a non-empty School_Id, THE Setup_Client SHALL store the returned School_Id as `sync_config.school_id`.
2. THE Institution_IPC SHALL store the server-generated School_Id without comparing the School_Id to the entered Massar_Code.
3. WHERE the Bootstrap_Function response returns a School_Id that differs from the entered Massar_Code, THE Institution_IPC SHALL complete setup successfully using the returned School_Id.
4. WHEN the Setup_Client stores the server-generated School_Id, THE Setup_Client SHALL store the entered Massar_Code as a separate descriptive field in `institution_config`, distinct from `sync_config.school_id`.
5. WHEN setup completes, THE Institution_IPC SHALL set the Firebase auth custom claim usage and the sync key to the value stored in `sync_config.school_id`.
6. WHEN the Bootstrap_Function response returns a School_Id that differs from a non-empty entered Massar_Code, THE Setup_Client SHALL display an informational confirmation message that setup will continue using the assigned identifier, and SHALL NOT require the user to modify the Massar_Code.
7. IF the Bootstrap_Function response indicates failure or lacks a non-empty School_Id, THEN THE Institution_IPC SHALL NOT write `sync_config.school_id`, SHALL preserve the prior configuration state without partial writes, and SHALL return an error indication.

### Requirement 5: Optional descriptive Massar_Code at setup

**User Story:** As a device owner setting up a new institution, I want the Massar code field to be optional and descriptive, so that I am not blocked from setup when I do not have or do not need to enter it.

#### Acceptance Criteria

1. WHERE the new-institution setup form is displayed, THE Setup_Client SHALL present the Massar_Code field with a visible indicator marking it as optional and SHALL NOT block form submission on the absence of a Massar_Code value.
2. WHEN the user submits the new-institution form with a Massar_Code that is empty or contains only whitespace characters, THE Setup_Client SHALL treat the Massar_Code as empty and SHALL allow the submission to proceed.
3. WHEN the user submits the new-institution form with a non-empty Massar_Code, THE Setup_Client SHALL trim leading and trailing whitespace, convert it to uppercase, and SHALL validate the trimmed value against the pattern `^[A-Z0-9]+$` with a maximum length of 20 characters.
4. IF the trimmed Massar_Code is non-empty and fails to match the pattern `^[A-Z0-9]+$` or exceeds 20 characters, THEN THE Setup_Client SHALL display a validation message indicating the Massar_Code format is invalid, SHALL NOT submit the form, and SHALL retain all values previously entered in the form.
5. WHEN the Setup_Client invokes `institution:setup-new` with an empty Massar_Code, THE Institution_IPC SHALL allow the operation to proceed.
6. THE Setup_Client SHALL determine whether to start setup independently of whether the Massar_Code is a valid Massar pattern.

### Requirement 6: Re-linking by Massar_Code lookup

**User Story:** As a device owner joining an already-provisioned institution, I want to re-link using the descriptive Massar code, so that the device connects to the correct existing institution without knowing the opaque School_Id.

#### Acceptance Criteria

1. WHEN the Relink_Operation receives a non-empty Massar_Code, THE Institution_IPC SHALL trim the Massar_Code and look up the existing institution whose stored Massar_Code matches the trimmed value.
2. WHEN the lookup finds exactly one institution matching the trimmed Massar_Code, THE Institution_IPC SHALL store that institution's School_Id as the local sync key.
3. IF the lookup finds no institution matching the trimmed Massar_Code, THEN THE Institution_IPC SHALL return an error response with an identifying error code and SHALL leave the existing local sync key unchanged.
4. IF the lookup finds more than one institution matching the trimmed Massar_Code, THEN THE Institution_IPC SHALL return an ambiguous-match error response with an identifying error code and SHALL leave the existing local sync key unchanged.
5. WHEN the Relink_Operation stores the looked-up School_Id, THE Institution_IPC SHALL use that School_Id as the value used as the Firestore partition key, distinct from the entered Massar_Code.
6. IF the provided Massar_Code is empty or contains only whitespace, THEN THE Institution_IPC SHALL return a validation error response and SHALL NOT perform a lookup.
7. IF the provided Massar_Code is non-empty and does not match the pattern `^[A-Z0-9]+$`, THEN THE Institution_IPC SHALL return a validation error response with an identifying error code and SHALL NOT perform a lookup.
8. IF the trimmed Massar_Code does not match any institution's stored descriptive Massar_Code field but matches the School_Id of an existing Legacy_Institution exactly, THEN THE Institution_IPC SHALL treat that Legacy_Institution's School_Id as the resolved match for the Relink_Operation.

### Requirement 7: Backward compatibility for already-configured institutions

**User Story:** As the owner of an institution configured before this feature, I want my existing identifier to keep working, so that my data and sync continue without disruption after the upgrade.

#### Acceptance Criteria

1. WHERE a Legacy_Institution has a stored School_Id equal to its Massar_Code, THE System SHALL continue using that stored School_Id, unchanged and without regeneration, as the Firestore partition key.
2. WHEN a Legacy_Institution device performs sync after the upgrade, THE System SHALL use the existing stored School_Id as the sync key without modifying its stored value.
3. WHEN the System reads the existing `sync_config.school_id` value, THE System SHALL use the stored value as-is and SHALL NOT regenerate, alter, or overwrite it.
4. WHEN a Legacy_Institution reports `Setup_Completed`, THE Setup_Client SHALL treat the institution as configured and SHALL NOT prompt for or require re-running new-institution setup.
5. WHERE a Legacy_Institution has no separate descriptive Massar_Code stored, THE System SHALL display the existing School_Id value as the Massar_Code until the user saves an edited Massar_Code value, after which THE System SHALL display the edited value.
6. IF a Legacy_Institution device's stored School_Id is missing, empty, or unreadable at sync time, THEN THE System SHALL use the alternative stored sync key (the stored Massar_Code) to continue the sync operation, SHALL complete sync without aborting, and SHALL leave the existing stored configuration values unchanged.
7. IF both the stored School_Id and the alternative stored sync key are missing, empty, or unreadable at sync time, THEN THE System SHALL abort the sync operation, SHALL surface an error indication identifying the missing identifier to the caller, and SHALL preserve all existing stored configuration values without modification.

### Requirement 8: Editing the Massar_Code as a simple field update

**User Story:** As a principal, I want to change the descriptive Massar code with a direct edit, so that I do not need an approval workflow to correct or update it.

#### Acceptance Criteria

1. WHEN a principal submits a new Massar_Code value that is non-empty, does not exceed 20 characters, and matches the pattern `^[A-Z0-9]+$`, THE System SHALL update the stored descriptive Massar_Code directly, exactly as it would update any other descriptive institution field (such as the institution name), with no approval step.
2. WHEN the stored Massar_Code is updated, THE System SHALL leave the School_Id, the Firestore partition key, and the sync key unchanged.
3. IF the submitted Massar_Code is non-empty and either exceeds 20 characters or does not match the pattern `^[A-Z0-9]+$`, THEN THE System SHALL return a validation error response indicating the invalid format and SHALL NOT update the stored Massar_Code.
4. IF the submitted Massar_Code is empty, THEN THE System SHALL return a validation error response indicating that the Massar_Code is required and SHALL NOT update the stored Massar_Code.
5. WHEN the stored Massar_Code update completes successfully, THE System SHALL return a success confirmation response to the principal.
6. IF persisting the updated Massar_Code fails, THEN THE System SHALL return an error response indicating that the update failed and SHALL retain the previously stored Massar_Code unchanged.
7. THE System SHALL persist an updated Massar_Code without requiring administrator approval.
8. IF the updated Massar_Code is confirmed as persisted by the remote System component but the subsequent local persistence attempt fails, THEN THE System SHALL treat the remotely confirmed value as authoritative, SHALL retry the local persistence at least once, and IF the retry also fails THEN THE System SHALL return a response indicating the update succeeded remotely but requires the operation to be retried to update the local cache.

### Requirement 9: Deprecation and simplification of the Identity_Change_Mechanism

**User Story:** As a maintainer, I want the identity-change approval mechanism removed or reduced, so that the codebase no longer carries complexity that only existed because the tenant key was mutable.

#### Acceptance Criteria

1. WHEN a user initiates a change to the descriptive Massar_Code, THE System SHALL process the change through the simple field-update path defined in Requirement 8 and SHALL NOT invoke the Identity_Change_Mechanism.
2. WHERE the Identity_Change_Mechanism is retained, THE System SHALL restrict its scope to institution-name changes only and SHALL leave the School_Id unchanged for every operation performed through that mechanism.
3. WHEN a user requests a change to the descriptive Massar_Code, THE System SHALL route the request through the direct field-update path and SHALL NOT create an identity-change approval request.
4. IF a request submitted to the Identity_Change_Mechanism attempts to modify the School_Id or the Massar_Code, THEN THE System SHALL reject the request with an error response that identifies the disallowed field and SHALL NOT apply any change.
5. THE System SHALL retain all previously submitted identity-change request records without deletion or modification, and SHALL keep those records retrievable for display through the existing read interface.
6. IF an existing pending identity-change request recorded before this feature includes a code-change component, THEN, WHEN that request is approved or applied, THE System SHALL reject the code-change portion with an error identifying the School_Id as immutable and SHALL NOT migrate or copy any data as a result of that request.

### Requirement 10: Predictable behavior across Cloud Function deployment state

**User Story:** As a device owner, I want clear behavior whether or not the updated Cloud Function is deployed, so that I am not left in an inconsistent state during the rollout.

#### Acceptance Criteria

1. IF the Setup_Client calls a Bootstrap_Function that is unavailable on the server, THEN THE Institution_IPC SHALL return an error response containing an identifying error code, SHALL display an error indication to the device owner stating that configuration could not be completed, and SHALL NOT mark the institution as configured.
2. IF a call to the Bootstrap_Function does not return a response within 30 seconds, THEN THE Institution_IPC SHALL treat the call as failed, SHALL return an error response containing an identifying error code, and SHALL NOT mark the institution as configured.
3. WHEN the deployed Bootstrap_Function returns a School_Id that is a non-empty string between 1 and 64 characters, THE Institution_IPC SHALL adopt the returned School_Id as the stored School_Id regardless of whether it equals the entered Massar_Code.
4. IF the deployed Bootstrap_Function returns a response that omits the School_Id or contains a School_Id that is empty or exceeds 64 characters, THEN THE Institution_IPC SHALL return an error response containing an identifying error code, SHALL retain any previously stored School_Id unchanged, and SHALL NOT mark the institution as configured.
5. WHILE the updated Bootstrap_Function is not yet deployed, THE System SHALL leave each already-configured institution operating on its existing stored School_Id without modification.
6. WHILE the updated Bootstrap_Function is not yet deployed, IF the Setup_Client submits a new-institution request with an empty Massar_Code, THEN THE Institution_IPC SHALL surface the not-yet-deployed server's rejection as a plain validation error without marking the institution as configured, and SHALL NOT crash, hang, or retry indefinitely.
