Short answer
The program has no concept of an educational cycle today. It is hard-wired to qualifying secondary (الثانوي التأهيلي). Managing primary and middle alongside it is either a deployment decision (one install per establishment) or a schema change (add a cycle dimension) — those are two very different amounts of work, and the choice comes first.

Here is what I found in the code.

What already works for any cycle
Three things are genuinely cycle-neutral and you can use them right now:

1. The user level mapping. settings.levelsMapping is a JSON map of section → Arabic level name, written by the Massar import (app.js:298 saveLevelsMapping). resolveLevelName(section, mapping) in
utils.js
 checks the user mapping first, then falls back to the hardcoded parser. So if you import a primary school's sections and map 1AP-1 → المستوى الأول ابتدائي, reporting groups correctly without touching code. This is the single biggest existing lever.

2. Core records. Students, grades, absences, correspondence are keyed on free-text section + school_year. A primary or collège section code stores and queries fine.

3. Page visibility. page_visibility is device-local and excluded from sync (per AGENTS.md). A primary-school install can hide التوجيه المدرسي, تتبع أوراق التحرير, and the lycée exam pages without affecting other devices.

The decision that comes first
Option A — one database per establishment. Each cycle gets its own install. This fits the current design exactly: institution_config is a single row, sync partitions by school_id_hash, page visibility is per-device. Zero schema change, zero risk. This is the correct answer if the three cycles are legally separate establishments — which they usually are.

Option B — one database, multi-cycle. Required only if a single director genuinely manages a combined establishment (مجموعة مدارس, مدارس الريادة) and needs one consolidated view. This needs a real cycle dimension and touches most of the app.

I'd take A unless you have a concrete combined-establishment requirement, and treat B as a roadmap.

If you go with Option B
Ordered so each phase is independently useful and low-risk:

Phase 1 — one level SSOT, cycle-tagged. Collapse the two dictionaries into a single shared module (the pattern already used by
system-tag-types.js
 and
orientation-error-contract.js
, which dual-export to main and renderer). Add a cycle field per entry and the missing 1AP–6AP / 1APIC–3APIC codes. Offset order by cycle (primary 100s, collège 200s, lycée 300s) so sortLevelNames and sortSectionNames stay stable. Have
exam-count-defaults.js
 require it instead of mirroring it — the current duplication is already a drift risk. This alone fixes level grouping across five pages.

Phase 2 — cycle in configuration. Add the active cycle(s) to institution_config (or a settings key) plus a selector in settings-school.html. It drives which levels appear in dropdowns and which page-visibility preset applies. Replaces the institution-name string parsing in the sidebar with real data.

Phase 3 — subject catalogue + evaluation model. A subjects(code, name_ar, cycle, weekly_hours, coefficient, order) table, and generalize the exam-count lookup to key on (cycle, level_code, subject) with fallback to (cycle,'*') then ('*','*'). Also fix exam-papers.js to be mapping-aware.

Phase 4 — teacher assignments junction. teacher_assignments(teacher_id, section, subject, weekly_hours, cycle, school_year). This is what makes both the polyvalent and specialist models expressible, and lets load and overtime be computed rather than stored as stale scalars.

Phase 5 — normalize the timetable. timetable_slots(day, period, teacher_id, section, subject, room, cycle, group_label, school_year). Your own audit already recommends this at

Phase 6 — orientation transitions. Add cycle and transition ('3APIC→TC', 'TC→1BAC') to orientation rows, and extend the existing error contract SSOT rather than forking it (AGENTS.md 028).
