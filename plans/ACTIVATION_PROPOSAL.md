# اقتراح نظام التفعيل — Gestion Scolaire

> تحليل شامل للوضع الحالي + اقتراح النموذج الأنسب

---

## 1. الوضع الحالي: ماذا لدينا؟

### التفعيل معطّل حاليا

```js
// main/licensing/service.js:16
const LICENSING_ENFORCEMENT_DISABLED = true;
```

كل البنية التحتية للتفعيل مبنية بالكامل لكنها **معطّلة**. التطبيق يعمل بدون أي قيود.

### ما هو مبني فعلا (وجاهز)

| المكوّن | الحالة | الملفات |
|---------|--------|---------|
| مفاتيح HMAC-SHA256 offline (`GSLK-...`) | مبني بالكامل | `main/licensing/offlineKey.js` |
| بصمة الجهاز (CPU, BIOS, MAC, RAM...) | مبني بالكامل | `main/licensing/deviceFingerprint.js` |
| نظام التجربة (Trial) مع حماية HMAC | مبني بالكامل | `main/licensing/trialService.js` |
| 3 خطط: basic (1 جهاز), pro (3), business (10) | مبني بالكامل | جدول `license_plans` |
| ربط المفتاح بـ Firebase عبر `authExchange` | مبني بالكامل | `firebase/functions/index.js` |
| لوحة Telemetry للمالك (أجهزة مفعّلة، heartbeat) | مبني بالكامل | `server/index.js`, `main/licensing/ownerSync.js` |
| واجهة التفعيل + لوحة الإدارة | مبنية بالكامل | `settings-license.html` |
| Fuzzy device matching (إعادة تثبيت بدون فقدان التفعيل) | مبني بالكامل | عتبة 70/100 |

### الثغرات الموجودة

| المشكلة | التفصيل |
|---------|---------|
| `generateSerial` غير مسجّل كـ IPC | الواجهة تنادي `window.api.licensing.generateSerial()` لكن لا يوجد handler في `licensing.js` |
| `saveConfig` و `testConnection` غير مسجّلين | مرجعيّين في الواجهة بدون handler في `ownerTelemetry.js` |
| السر الواحد (`GESTION_LICENSE_SECRET`) | نفس السر يُستخدم محليا + Firebase + CLI — لو تسرّب يصبح لكل نسخة إمكانية توليد مفاتيح |

## 2. تحليل: أي نموذج يناسبك؟

### طبيعة التطبيق

| الخاصية | القيمة | الأثر على نموذج التفعيل |
|---------|--------|------------------------|
| الهدف | ثانويات تأهيلية مغربية | بيئة محدودة الإنترنت، حساسة للسعر |
| البنية | Electron desktop + SQLite | لا يمكن فرض SaaS حقيقي |
| الاتصال | offline-first، Firebase اختياري | لا يمكن الاعتماد على validation عبر الإنترنت |
| العملاء | مؤسسات تعليمية (ليس أفراد) | دورة مبيعات B2B، عقود سنوية |
| البيانات | حساسة (بيانات تلاميذ) | يجب أن تبقى محلية أصلا |
| التحديثات | عبر GitHub Releases + electron-updater | يمكن ربط التحديث بحالة الترخيص |

### مقارنة النماذج الممكنة

| النموذج | الملاءمة | السبب |
|---------|----------|-------|
| SaaS شهري (subscription online) | **غير مناسب** | المدارس بدون إنترنت مستقر، SQLite محلي لا يتحول لـ SaaS |
| Machine-based perpetual (شراء لمرة واحدة) | **جيد جزئيا** | يناسب offline لكن لا يضمن إيرادات متكررة |
| **Machine-based + اشتراك سنوي** | **الأنسب** | يجمع بين offline-first + إيرادات متكررة + تحديثات |
| Subscription online فقط | **غير مناسب** | يتعارض مع offline-first |
| Freemium + Pro | **ممكن** | لكن صعب التحكم في الحدود بدون backend |

## 3. النموذج المقترح: Hybrid Machine-Subscription

### الفلسفة

> **مفتاح مرتبط بالجهاز + اشتراك سنوي للتحديثات والدعم + طبقة Firebase اختيارية**

```
┌─────────────────────────────────────────────────────────────────┐
│                    نموذج التفعيل المقترح                        │
│                                                                 │
│  ┌──────────┐    ┌──────────────┐    ┌────────────────────┐     │
│  │  Trial   │───▶│  Activation  │───▶│  Annual Renewal    │     │
│  │ 30 يوم   │    │  مفتاح GSLK  │    │  مفتاح تجديد سنوي │     │
│  └──────────┘    └──────────────┘    └────────────────────┘     │
│       │                │                       │                │
│       ▼                ▼                       ▼                │
│  ┌──────────┐    ┌──────────────┐    ┌────────────────────┐     │
│  │ محدود    │    │  كامل        │    │  تحديثات + دعم     │     │
│  │ الوظائف  │    │  الوظائف     │    │  + Firebase sync   │     │
│  └──────────┘    └──────────────┘    └────────────────────┘     │
└─────────────────────────────────────────────────────────────────┘
```

### الخطط المقترحة (4 بدل 3)

| الخطة | الكود | الأجهزة | السعر المقترح (MAD/سنة) | الجمهور | Firebase Sync |
|-------|-------|---------|------------------------|---------|---------------|
| **مجاني** | `free` | 1 | 0 | تجريب، مدارس صغيرة جدا | لا |
| **أساسي** | `basic` | 2 | 1,500 | مدرسة واحدة، إدارة محلية | لا |
| **احترافي** | `pro` | 5 | 3,500 | مدرسة مع عدة مستخدمين | نعم |
| **مؤسساتي** | `enterprise` | 15 | 8,000 | أكاديمية / عدة مدارس | نعم + أولوية دعم |

### ما يتغير في كل خطة

#### الخطة المجانية (`free`)
```
الوظائف المتاحة:
  ✅ إدارة التلاميذ (حد أقصى 200 تلميذ)
  ✅ تسجيل الغياب
  ✅ استيراد الجداول (FET)
  ❌ النقط والامتحانات
  ❌ التقارير والطباعة
  ❌ النسخ الاحتياطي التلقائي
  ❌ Firebase sync
  ❌ التحديثات التلقائية
```

#### الخطة الأساسية (`basic`)
```
الوظائف المتاحة:
  ✅ كل وظائف المجاني بدون حدود
  ✅ النقط والامتحانات
  ✅ التقارير والطباعة
  ✅ النسخ الاحتياطي
  ❌ Firebase sync
  ✅ التحديثات التلقائية (سنة واحدة)
```

#### الخطة الاحترافية (`pro`)
```
الوظائف المتاحة:
  ✅ كل وظائف الأساسي
  ✅ Firebase sync (مزامنة سحابية)
  ✅ تعدد المستخدمين مع الأدوار
  ✅ لوحة الإحصائيات المتقدمة
  ✅ التحديثات التلقائية (سنة واحدة)
  ✅ دعم عبر البريد
```

#### الخطة المؤسساتية (`enterprise`)
```
الوظائف المتاحة:
  ✅ كل وظائف الاحترافي
  ✅ إدارة عدة مؤسسات
  ✅ تقارير مجمّعة
  ✅ API مخصص
  ✅ دعم أولوي + تركيب
```

```js

        reports: false,

    basic: {
        maxStudents: Infinity,
        grades: true,
        reports: true,
        backup: true,
        firebaseSync: false,
        autoUpdate: true,       // لمدة سنة الاشتراك
        advancedAnalytics: false,

    pro: {
        maxStudents: Infinity,
```

```
     مفتاح أصلي (GSLK-xxxx)
     expires_at: 2026-09-01
            │
            │  ← قبل الانتهاء بـ 30 يوم: تنبيه في التطبيق
            │
            ▼
     ┌──────────────┐
     │  انتهى؟      │
     │   /     \     │
     │  لا     نعم   │
     │  │       │     │
     │  ▼       ▼     │
     │ عادي  Grace    │
     │       30 يوم   │── ← التطبيق يعمل لكن مع تنبيه دائم
     │         │      │
     │         ▼      │
     │    انتهى Grace │
     │         │      │
     │         ▼      │
     │   تنزيل لخطة  │
     │    free        │── ← لا يفقد بياناته، فقط الوظائف المتقدمة
     └──────────────┘

     التجديد: مفتاح GSLK جديد بنفس customerRef
     → يحدّث expires_at دون فقدان الأجهزة المفعّلة
```

**لماذا هذا النهج؟**
- المدرسة لا تفقد بياناتها أبدا (حتى لو لم تجدد)
- تنزل لخطة `free` وليس إغلاق كامل
- الضغط للتجديد يأتي من فقدان الوظائف المتقدمة (تقارير، نقط) وليس من فقدان البيانات
- هذا أخلاقيا أفضل ويبني ثقة مع المؤسسات التعليمية

### 4.5 أمان السر (`GESTION_LICENSE_SECRET`)

**المشكلة الحالية:** نفس السر يُستخدم في 3 أماكن (CLI، Electron، Firebase). لو تمّ reverse-engineering للتطبيق، يمكن توليد مفاتيح.

**الحل المقترح — مفتاحين:**

```
┌─────────────────────────────────────────────┐
│  GESTION_LICENSE_SIGN_SECRET                │
│  ← يبقى فقط عندك (CLI + Firebase)          │
│  ← يُستخدم لـ generateSerialKey()          │
│  ← لا يُوزّع أبدا مع التطبيق              │
├─────────────────────────────────────────────┤
│  GESTION_LICENSE_VERIFY_SECRET              │
│  ← مشتق من SIGN_SECRET عبر HKDF            │
│  ← يُضمّن في التطبيق (أقل خطورة)           │
│  ← يُستخدم فقط لـ decodeOfflineLicenseKey() │
│  ← لا يمكنه توليد مفاتيح جديدة            │
└─────────────────────────────────────────────┘
```

> **ملاحظة:** هذا يتطلب الانتقال من HMAC متماثل إلى نظام asymmetric (مثل Ed25519 signatures). المفتاح العام يُوزّع مع التطبيق للتحقق فقط، والمفتاح الخاص يبقى عند المطوّر فقط للتوقيع.
