# Phase 7: Institution Device Linking (ربط أجهزة المؤسسة)

## Context

The DynamoDB sync infrastructure is complete (Phases 1-6): push engine, pull engine, conflict resolution, settings UI. But currently, linking devices to an institution is **implicit and confusing** — the admin manually enters a `licenseKey` in sync settings, and the Lambda maps it to a `schoolId`. There's no onboarding flow, no device management, and no visible institution identity.

This phase adds a **first-run setup screen** and **OTP-based device linking** so that:

- The first device creates the institution using the school's MASSAR code (Ministry identifier)
- Additional devices link by entering the MASSAR code + a 6-digit OTP generated by the admin
- The admin can manage linked devices from the sync settings page

## Design Decisions

| Decision               | Choice                                                                |
| ---------------------- | --------------------------------------------------------------------- |
| Institution identifier | MASSAR code (Ministry school code)                                    |
| Setup timing           | First-run screen, before login                                        |
| Device linking auth    | 6-digit OTP (10 min TTL), generated by admin                          |
| Connectivity           | Hybrid — new institution works offline; linking needs LAN or internet |
| OTP verification       | LAN first (UDP discovery + HTTP verify), server fallback (Lambda)     |

## Phase 7.2: OTP Module

### New file: `main/linking/otp.js`

- `generateOtp(db, massarCode, creatorDeviceHash)` → `{ otp, expiresAt }`
    - `crypto.randomInt(100000, 999999)` for 6-digit code
    - Hash with existing `hashPassword()` from [main/auth/password.js](main/auth/password.js)
    - Invalidate any previous active OTP for same MASSAR code
- `verifyOtp(db, massarCode, otpPlaintext, consumerDeviceHash)` → `{ valid, error? }`
    - Verify against stored hash using `verifyPassword()`
    - Rate-limit: max 5 failures per MASSAR code per 10-min window
    - Mark as `used` on success
- `cleanupExpiredOtps(db)` — periodic cleanup
- `getActiveOtp(db, massarCode)` — check if OTP exists and time remaining

### Reused utilities

- `hashPassword()` / `verifyPassword()` from [main/auth/password.js](main/auth/password.js) (scrypt-based)
- `collectCurrentFingerprint()` from [main/licensing/deviceFingerprint.js](main/licensing/deviceFingerprint.js) for device identification

## Phase 7.3: LAN Discovery & Verification

### New file: `main/linking/lan.js`

When admin generates OTP, Device 1 starts two services:

1. **UDP Broadcast (Discovery)** — port 19877
    - Sends every 3s: `{"service":"pencil2-link","massar":"<code>","port":19876,"deviceName":"<hostname>"}`
    - Stops when OTP expires or is consumed

2. **HTTP Server (Verification)** — port 19876
    - `POST /verify-link` with body `{massar, otp, deviceHash, deviceName}`
    - Success response includes sync config + user accounts
    - Failure response with error message

3. **UDP Listener (Client)** on Device 2
    - Listens for broadcast beacons, filters by MASSAR code
    - Returns Device 1's IP and port

**Functions:**

- `await startLinkingServer(db)` → `{ port, address }`
- `stopLinkingServer()`
- `discoverLanDevices(massarCode, timeoutMs)` → `[{ip, port, deviceName}]`
- `verifyViaLan(targetIp, targetPort, massar, otp, deviceHash, deviceName)` → result

Uses built-in Node.js `dgram` + `http` — no new dependencies.

## Phase 7.4: Server-Side OTP (Lambda + DynamoDB)

### New file: `main/linking/server.js`

For when devices are NOT on the same LAN.

**DynamoDB OTP Item:**

- `PK: OTP#<massar>`, `SK: ACTIVE`
- `otpHash`, `syncConfigPayload` (AES-256 encrypted with OTP as key material)
- `TTL` attribute for auto-cleanup

**Two new Lambda actions** (extend existing auth Lambda at [infra/lib/auth-lambda/](infra/lib/auth-lambda/)):

1. `POST /link/publish-otp` — Device 1 publishes OTP hash + encrypted config (requires licenseKey auth)
2. `POST /link/verify-otp` — Device 2 verifies OTP, gets encrypted config (no auth — OTP IS the auth)

**Hybrid verification strategy on Device 2:**

1. Attempt LAN discovery (5s timeout)
2. If found → verify via LAN
3. If not found → fall back to server verification
4. Show progress: "جاري البحث في الشبكة المحلية..." → "جاري التحقق عبر السيرفر..."

- [infra/lib/sync-stack.ts](infra/lib/sync-stack.ts) — add Lambda permissions for OTP endpoints

## Phase 7.5: First-Run Setup Page

### New files: `setup.html` + `js/pages/setup.js`

Full-screen page (no sidebar, no header). Two-step flow:

**Step 1: Choose mode**

- Card A: "مؤسسة جديدة" (New institution) — first device in the school
- Card B: "ربط بمؤسسة موجودة" (Link to existing) — additional device

**Step 2a — New institution:**

1. MASSAR code input (validated format)
2. Institution name (optional)
3. Admin account creation (name, password, confirm)
4. On submit: store config → create admin → register device → redirect to `index.html`

**Step 2b — Link to existing:**

1. MASSAR code input
2. 6-digit OTP input (large digit boxes)
3. On submit: LAN discovery → LAN verify → server fallback → import config → redirect to `index.html`

### Startup redirect in `main.js`

At [main.js:158](main.js#L158), change `window.loadFile('index.html')` to:

```js
const db = getDb();
const inst = db.prepare('SELECT setup_completed FROM institution_config WHERE id = 1').get();
const targetPage = !inst || !inst.setup_completed ? 'setup.html' : 'index.html';
window.loadFile(targetPage);
```

## Phase 7.8: Sync Integration

1. **MASSAR as schoolId**: `institution_config.massar_code` becomes the canonical `schoolId` used in `sync_config.school_id` and as the DynamoDB partition key `SCHOOL#<massar>`
2. **Auto-config on link**: When Device 2 links via OTP, sync config is auto-populated from Device 1's response (authLambdaUrl, awsRegion, licenseKey, syncInterval)
3. **Device heartbeat**: Each sync cycle updates `linked_devices.last_seen_at` for the current device
4. **Revocation enforcement**: Revoked device hash pushed to DynamoDB; pull engine checks for self-revocation
