# خطة مركز الاستيراد المركزي الذكي متعدد الملفات

> **التاريخ:** 2026-07-15  
> **الحالة:** مقترح للتنفيذ — لم تُنفذ التغييرات البرمجية الواردة في هذه الوثيقة  
> **النطاق:** إعادة تصميم `settings-imports.html` وبناء طبقة تنسيق ذكية فوق مستوردات البيانات الحالية  
> **المنصة الحالية:** Electron 35، JavaScript في الواجهة، Electron IPC/contextBridge، وSQLite عبر `better-sqlite3`  
> **وثيقة مرتبطة:** `docs/superpowers/plans/2026-04-07-data-integration-master-data-management.md`

## 1. الملخص التنفيذي

الخيار المعتمد هو **حل هجين** يجمع بين:

1. **مركز استيراد مركزي واحد** داخل `settings-imports.html` لإدارة تغذية التطبيق بالبيانات.
2. **منطقة استيراد ذكي متعدد الملفات** تقبل دفعة مختلطة، وتحلل كل ملف على حدة، وتقترح وجهته مع درجة ثقة وتحذيرات قبل أي كتابة.
3. **اختصارات سياقية من الصفحات الوظيفية** تنقل المستخدم إلى المركز مع تحديد النوع المتوقع، مثل `settings-imports.html?type=grades`، من دون نسخ منطق الاستيراد إلى كل صفحة.
4. **الإبقاء على الاستيراد اليدوي الحالي** كخيار دقيق واحتياطي داخل قسم ثانوي قابل للطي.
5. **فصل النسخ الاحتياطي والاستعادة** بصريًا ومفاهيميًا عن استيراد بيانات التلاميذ والنقط والغياب واستعمال الزمن.

لا يُعتمد زر استيراد عائم في أسفل كل صفحة، ولا استيراد تلقائي صامت. المركز الواحد يقلل تكرار المنطق، بينما تمنع مرحلة المراجعة أخطاء التصنيف والكتابة في السنة أو القسم غير الصحيح.

## 2. الأهداف

- تمكين المستخدم من إسقاط أو اختيار ملفات متعددة ومختلطة في عملية واحدة.
- تصنيف **كل ملف منفردًا** اعتمادًا على بنيته ومحتواه، وليس اسمه وامتداده فقط.
- عرض النوع المكتشف، درجة الثقة، السنة الدراسية/الدورة، عدد السجلات، والتحذيرات قبل التنفيذ.
- ترتيب التنفيذ حسب الاعتماد بين البيانات مع منع تشغيل ملف يعتمد على بيانات لم تُجهز بعد.
- إعادة استخدام مستوردات التطبيق الحالية بدل إعادة كتابتها دفعة واحدة.
- توفير تقدم واضح، أخطاء مرتبطة بكل ملف، إعادة محاولة انتقائية، وملخص نهائي قابل للمراجعة.
- الحفاظ على توافق الاستيراد اليدوي والمسارات الحالية أثناء الانتقال التدريجي.
- تحسين الوصول، دعم RTL، الاستجابة للأحجام المختلفة، الوضع الداكن، وتقليل الحركة.

## 3. ما لا تستهدفه الخطة

- لا تنفذ هذه الوثيقة التغييرات البرمجية؛ هي خطة فقط.
- لا تعيد كتابة `js/pages/settings-imports.js` بالكامل في خطوة واحدة.
- لا تنقل الاستيراد إلى كل صفحة وظيفية ولا تنشئ منطق استيراد مكررًا.
- لا تنفذ استيرادًا صامتًا بمجرد إسقاط الملف.
- لا تعدّل صيغة ملفات المصادر الخارجية.
- لا توحّد النسخ الاحتياطي مع استيراد البيانات التشغيلية.
- لا تضيف جداول مهام دائمة إلى قاعدة البيانات في المرحلة الأولى.
- لا تعد بنظام rollback شامل لكل أنواع الاستيراد قبل توثيق حدود كل مستورد وواجهات IPC التي يستخدمها.

## 4. الوضع الحالي الموثق

### 4.1 نقاط الدخول الحالية

- صفحة المركز الحالية: `settings-imports.html`.
- متحكم الصفحة: `js/pages/settings-imports.js`.
- `runImport(action)` يفتح حقل ملفات مخفيًا يحدده جدول `FILE_INPUTS`.
- `initDropZone()` يستقبل الملفات المسقطة، ثم يستدعي `inferImportActionFromFiles(files)` مرة واحدة للدفعة كلها، يطلب التأكيد، وبعده يستدعي `handleImport(action, files)`.
- `handleImport(action, files)` يعالج الدفعة كلها كنوع واحد، ويوجه إلى مسارات التلاميذ أو النقط أو الغياب أو FET أو Agent XML أو وضعية التلميذ.

### 4.2 حدود الاكتشاف الحالي

`inferImportActionFromFiles(files)` يعتمد أساسًا على الاسم والامتداد:

- XML باسم يطابق `/^\d{4,6}[a-z]?_/i` يُعامل كـ `agent-xml`.
- XML آخر يُعامل كـ `fet`.
- بعض كلمات الاسم تشير إلى الغياب أو النقط أو التلاميذ.
- عند غياب إشارة واضحة: عدة ملفات تُعامل كنقط، وملف واحد كتلاميذ.

هذا السلوك مناسب كاختصار أولي، لكنه غير كافٍ لدفعة مختلطة أو لأسماء ملفات عامة؛ كما أنه يقرر نوعًا واحدًا للدفعة بدل قرار مستقل لكل ملف.

### 4.3 مستوردات موجودة يجب الحفاظ عليها أولًا

الدوال التالية موجودة حاليًا في `js/pages/settings-imports.js` ويجب معاملتها كمنفذات/Adapters أولية:

- `importStudents`
- `importGrades`
- `importAbsences`
- `importFetXml`
- `importAgentXml`
- `importStudentStatus`

كما توجد وظائف مساندة حالية منها:

- `detectSchoolYearFromWorkbook`
- `checkYearMismatch`
- `updateImportProgress`
- `renderImportStatusPanel`
- `logImport`

`logImport(action, details)` يسجل عبر `window.api.systemLogs.add` بقيمة `action` تبدأ بـ `import:`، لكنه ليس سجل جلسة استيراد دائمًا ولا يحفظ دورة حياة كل ملف.

### 4.4 التكامل والتحقق الحاليان

- `js/data-source-registry.js` يحتفظ في `localStorage` بمصدر البيانات الناجح وبيانات وصفية وتحذيرات حسب السنة الدراسية. مفتاح التخزين هو `dataSourceRegistry`. لا يمثل Jobs دائمة ولا طابور ملفات.
- `js/cross-source-validator.js` يوفر `CrossSourceValidator.validateAfterImport(importType, importedData)` لمسارات `grades` و`absences` و`fet` و`agent_xml`. لا يرمي أخطاء عمدًا، بل يعيد `{ valid, warnings }`.
- `js/name-resolver.js` يوفر `NameResolver.normalizeName` و`resolve` و`resolveAsync` للتطابق الدقيق، تبديل أجزاء الاسم، إزالة الألقاب، skeleton للنقل الصوتي، fuzzy matching، ثم aliases من قاعدة البيانات عند توفر API.
- الخطة السابقة `docs/superpowers/plans/2026-04-07-data-integration-master-data-management.md` أنشأت أساس NameResolver وCrossSourceValidator وDataSourceRegistry ولوحة حالة الاستيراد. الخطة الحالية **تستخدم هذا الأساس ولا تستبدله**.

### 4.5 الذرية الحالية

- مسار الغياب يجهز الصفوف المستخرجة كاملة في الذاكرة أولًا، ثم ينفذ `window.api.absences.saveBulk(absences)` بعد نجاح القراءة ووجود سجلات صالحة؛ لا يستدعي `deleteByYear` داخل `importAbsences`.
- لا يوجد حاليًا Job transaction موحد يغطي كل أنواع الاستيراد في دفعة مختلطة.
- لا توجد، حسب الفحص الحالي، جداول `import_jobs` أو `import_files` أو `import_errors`.

### 4.6 النسخ الاحتياطي مسار مستقل

`js/backup.js` يدير نسخ `localStorage` وSQLite واستعادتهما عبر `BackupManager` وواجهات `window.api.system` المتاحة. لذلك يجب أن يظهر في منطقة مستقلة باسم واضح مثل **النسخ الاحتياطي والاستعادة**، لا داخل مسار **تغذية التطبيق بالبيانات**.

### 4.7 مصدر الأنماط

- مصدر التعديل: `css/tailwind-input.css`.
- `css/tailwind-output.css` ناتج مولد ولا يُعدّل يدويًا.
- توجد مكونات حالية مثل `.import-status-panel` و`.imports-action-card` يمكن تطويرها أو استبدالها تدريجيًا.

## 5. المشكلات التي تعالجها الخطة

### 5.1 تجربة الاستخدام

- قرار واحد لكل الدفعة يجعل الملفات المختلطة عرضة للتوجيه الخاطئ.
- الاعتماد على الاسم والامتداد لا يمنح المستخدم تفسيرًا أو درجة ثقة.
- التأكيد الحالي يسبق فحصًا غنيًا لمحتوى كل ملف.
- لا يوجد طابور مرئي موحد يوضح حالة كل ملف واعتماداته.
- يصعب ربط الأخطاء بملف وصف أو ورقة محددة، ثم إعادة محاولة الملف وحده.
- بطاقات الاستيراد المتعددة تناسب المستخدم الخبير، لكنها لا تقدم مدخلًا بسيطًا للمستخدم الذي يملك مجموعة ملفات غير مرتبة.
- النسخ الاحتياطي والاستيراد التشغيلي متقاربان في الصفحة رغم اختلاف غرضهما ومخاطرهما.

### 5.2 المعمارية

- `js/pages/settings-imports.js` متحكم كبير يجمع العرض، القراءة، الاكتشاف، التحقق، والتنفيذ.
- `handleImport` مرتبط بشكل مباشر بالتفاعل وبمنفذات الأنواع.
- لا يوجد نموذج جلسة موحد ولا عقد نتيجة موحد بين المستوردات.
- التحقق الحالي بعد الاستيراد في CrossSourceValidator؛ المطلوب إضافة Preflight قبل الكتابة مع الإبقاء على التحقق اللاحق.
- لا توجد آلية موحدة لتحديد الاعتمادات أو الإلغاء أو إعادة المحاولة على مستوى الملف.

## 6. قرارات التصميم والمعمارية

### 6.1 المركز هو المصدر الوحيد لمنطق الاستيراد

أي اختصار في صفحة النقط أو الغياب أو التلاميذ يفتح المركز مع سياق فقط. مثال مقترح:

```text
settings-imports.html?type=grades&year=2026-2027
```

المعاملات المقترحة:

- `type`: تلميح نوع أولي، لا يتجاوز تحليل المحتوى.
- `year`: سنة متوقعة تُقارن بالسنة المكتشفة.
- `source`: اسم الصفحة التي أطلقت الاختصار لأغراض العودة/القياس.

يجب ألا يؤدي Query Parameter إلى تنفيذ تلقائي؛ يجهز الواجهة أو يرفع أولوية نوع معين فقط.

### 6.2 طبقة Orchestrator فوق المنفذات الحالية

يُضاف مصنف ومنسق جديدان فوق الدوال الحالية. في البداية لا تتغير قواعد كتابة البيانات داخل كل مستورد إلا بالحد الأدنى اللازم لإرجاع نتيجة موحدة.

### 6.3 تحليل المحتوى قبل الكتابة

كل ملف يمر بمراحل: قراءة آمنة، اكتشاف signature، استخراج metadata، تصنيف، Preflight، مراجعة، ثم تنفيذ. لا تبدأ الكتابة أثناء التحليل.

### 6.4 المستخدم يملك القرار النهائي

- التصنيف الواثق يُعرض كاقتراح جاهز، لا كتنفيذ تلقائي.
- التصنيف المتوسط يحتاج مراجعة مرئية.
- التصنيف المنخفض أو المتعارض يحتاج اختيار نوع يدوي.
- تعديل المستخدم للنوع يعيد Preflight الخاص بالملف.

### 6.5 انتقال تدريجي لا Big-bang rewrite

كل حزمة عمل يجب أن تبقي المسارات اليدوية قابلة للاستخدام. يتم استخراج الوحدات عندما يصبح عقدها واضحًا، وليس لمجرد تقليل حجم الملف.

## 7. تجربة الاستخدام المستهدفة

### 7.1 ترتيب الصفحة

1. **حالة الجاهزية وربط البيانات:** السنة النشطة، المصادر المتوفرة، التحذيرات العابرة للمصادر.
2. **منطقة الاستيراد الذكي:** اختيار/سحب ملفات متعددة مع صياغة واضحة للأنواع المقبولة.
3. **طابور الملفات والمراجعة:** صف لكل ملف مع النوع والثقة والسنة والحالة والإجراءات.
4. **حل التعارضات:** نوع غير مؤكد، سنة مختلفة، أسماء غير محلولة، أو اعتماد ناقص.
5. **التنفيذ والتقدم:** تقدم عام وتقدم لكل ملف مع منع النقر المتكرر.
6. **ملخص النتائج:** نجح/فشل/تخطي، السجلات المكتوبة، التحذيرات، وخيارات إعادة المحاولة.
7. **الاستيراد اليدوي:** البطاقات الحالية داخل Accordion ثانوي بعنوان «اختيار نوع الاستيراد يدويًا».
8. **السجل:** آخر عمليات الاستيراد الحالية، مع فصل واضح بين سجل النظام ونتائج الجلسة الحالية.
9. **إدارة البيانات والحذف:** منطقة تحذيرية مستقلة.
10. **النسخ الاحتياطي والاستعادة:** قسم مستقل بصريًا ومفاهيميًا.

## 8. نموذج الحالة المقترح

> النماذج التالية **مقترحة** وليست أنواعًا موجودة حاليًا في الكود.

### 8.1 `ImportSession`

```js
{
  id,                    // UUID داخل الواجهة في المرحلة الأولى
  createdAt,
  expectedYear,
  sourceContext,         // query params / manual / drop
  status,                // collecting | reviewing | ready | importing | completed | cancelled
  files: ImportFileItem[],
  dependencyGraph,
  totals: {
    files,
    ready,
    succeeded,
    failed,
    skipped,
    recordsWritten,
    warningCount,
    errorCount
  }
}
```

### 8.2 `ImportFileItem`

```js
{
  id,
  file,                  // File object، غير دائم في المرحلة الأولى
  name,
  extension,
  size,
  fingerprint,           // اختياري لكشف التكرار داخل الجلسة
  status,                // queued | analyzing | needs_review | ready |
                         // importing | succeeded | failed | skipped
  detectedType,
  selectedType,
  confidence,            // 0..1
  evidence: [],          // headers/root/signatures التي أدت للقرار
  detectedYear,
  detectedTerm,
  sheetNames: [],
  recordEstimate,
  preflight: {
    valid,
    warnings: [],
    errors: [],
    unresolved: []
  },
  dependencies: [],
  progress,
  result,
  retryCount
}
```

### 8.3 انتقالات الحالة

```text
queued
  → analyzing
      → ready
      → needs_review → analyzing (بعد تعديل النوع/السنة) → ready
      → failed
ready
  → importing
      → succeeded
      → failed → ready (إعادة المحاولة)
أي حالة غير importing
  → skipped
```

- لا يسمح بالانتقال إلى `importing` إذا كان Preflight غير صالح.
- `failed` يجب أن يحتفظ بالخطأ والسياق كي لا يضطر المستخدم لإعادة تحليل جميع الملفات.
- إلغاء الجلسة يمنع بدء ملفات جديدة؛ لا يدعي إلغاء كتابة جارية ما لم يدعم المستورد ذلك فعليًا.

## 9. خط أنابيب التصنيف الذكي

### 9.1 المراحل

1. **فحص الملف الأساسي:** الحجم، الامتداد، MIME إن توفر، وعدم قبول ملف فارغ.
2. **قراءة آمنة:** قراءة الحد الأدنى الضروري. في Excel تُقرأ أسماء الأوراق والعناوين وعينة محدودة؛ في XML يُقرأ root والعناصر المميزة دون كتابة.
3. **استخراج signatures:**
   - عناوين أعمدة مميزة.
   - أسماء أوراق متوقعة.
   - XML root/namespaces والعناصر الأساسية.
   - أنماط القيم مثل PPR، القسم، المادة، التاريخ، الحصة، أو النقطة.
4. **Scoring متعدد الأدلة:** كل مستورد يعيد score وأسبابًا قابلة للعرض.
5. **اكتشاف السنة/الدورة:** يعاد استخدام `detectSchoolYearFromWorkbook` حيث ينطبق، مع توسيعه عبر Adapter بدل ربط المصنف بالواجهة.
6. **حل التعارض:** مقارنة التلميح من الاسم، التلميح من Query Parameter، والـsignature الفعلية. المحتوى له أولوية، والتعارض يظهر للمستخدم.
7. **Fallback يدوي:** إذا لم يوجد فائز واضح، يختار المستخدم النوع من قائمة، ثم يعاد التحليل وفق النوع المختار.

### 9.2 درجات الثقة المقترحة

> هذه الحدود **قرار تصميم مقترح** وتحتاج معايرة على عينات حقيقية؛ ليست سلوكًا موجودًا الآن.

- `>= 0.85`: ثقة عالية؛ يعرض «جاهز» إذا نجح Preflight.
- `0.60–0.84`: ثقة متوسطة؛ يعرض «راجع النوع المقترح».
- `< 0.60`: ثقة منخفضة؛ يتطلب اختيارًا يدويًا.
- إذا كان الفرق بين أعلى نتيجتين أقل من `0.10`، تعد النتيجة ملتبسة حتى لو تجاوزت الأعلى `0.60`.

### 9.3 عقد المصنف المقترح

```js
class ImportClassifier {
  async classify(file, context) {
    return {
      type,
      confidence,
      evidence,
      alternatives,
      metadata,
      needsReview
    };
  }
}
```

يجب أن تكون الأدلة مفهومة مثل «وجدت أعمدة رمز التلميذ، المادة، النقطة» بدل score مجرد.

## 10. Preflight دون كتابة

لكل نوع Adapter جديد ذو مرحلتين واضحتين:

```js
{
  analyze(file, context),     // لا كتابة
  execute(prepared, context)  // كتابة بعد التأكيد
}
```

يجب أن يغطي Preflight حسب النوع:

- صلاحية الملف والبنية والعناوين المطلوبة.
- السنة الدراسية والدورة ومطابقتهما للسياق النشط.
- الأوراق/الصفوف التي ستقرأ والتي ستتجاهل مع السبب.
- عدد السجلات المتوقع.
- التكرارات داخل الملف وداخل الدفعة عند الإمكان.
- الأقسام والمواد والتلاميذ والمدرسون غير المعروفين.
- الأسماء غير المحلولة عبر `NameResolver` عند الحاجة.
- الاعتمادات الناقصة، مثل نقط تشير إلى تلاميذ غير موجودين.
- معاينة صغيرة لنتيجة التحويل دون حفظ.

`CrossSourceValidator.validateAfterImport` يبقى تحققًا لاحقًا. لا ينبغي الادعاء أنه Preflight؛ يمكن استخراج قواعد قابلة لإعادة الاستخدام منه تدريجيًا، مع الحفاظ على عقده الحالي.

## 11. ترتيب الاعتماد والتنفيذ

### 11.1 الترتيب الافتراضي المقترح

```text
students → agent_xml → fet → grades → absences → status
```

هذا ترتيب أمان ابتدائي، وليس قاعدة صلبة لكل ملف. الأفضل بناء **DAG** اعتماد فعلي:

- ملف لا يعتمد على غيره يمكن تشغيله بالتوازي لاحقًا إذا كانت واجهات الكتابة آمنة.
- ملف النقط يعتمد على توفر التلاميذ/الأقسام والمواد اللازمة في سياقه.
- ملف الغياب يعتمد على التلاميذ والأقسام.
- ملفات Agent XML وFET قد تغذي كيانات يستخدمها التحقق في ملفات لاحقة.
- وضعية التلميذ تأتي بعد تثبيت بيانات التلاميذ.

### 11.2 خوارزمية التنفيذ

1. يبني المنسق العقد والروابط من نتائج Preflight.
2. يمنع الملف إذا كان اعتماد لازم `failed` أو `needs_review`.
3. يعرض سبب الانتظار نصيًا، لا بلون فقط.
4. ينفذ العقد الجاهزة بحسب topological order.
5. في المرحلة الأولى يفضل التنفيذ التسلسلي لتقليل المخاطر.
6. التوازي تحسين لاحق لا يُفعل قبل التحقق من تعارضات SQLite وواجهات IPC.

## 12. الذرية والاسترجاع

### 12.1 سياسة المرحلة الأولى

- **وحدة النجاح الأساسية هي الملف/النوع، لا الدفعة المختلطة كلها.**
- فشل ملف لا يمحو تلقائيًا ملفات سابقة نجحت، لكن يوقف الملفات التابعة له.
- تعرض الواجهة بوضوح أن الدفعة قد تنتهي بنجاح جزئي.
- لا يكتب أي ملف قبل نجاح Preflight وتأكيد المستخدم.

### 12.2 حسب النوع

- **الغياب:** الحفاظ على staging الحالي الذي يتطلب نجاح قراءة الملفات قبل `deleteByYear` و`saveBulk`. يلزم لاحقًا فحص ما إذا كانت عمليتا الحذف والحفظ داخل transaction واحدة في طبقة IPC؛ إن لم تكونا كذلك، يقترح إضافة أمر IPC ذري خاص بالاستبدال.
- **الأنواع الأخرى:** توثيق كل أوامر الكتابة والتحديث/الحذف التي يستعملها المستورد قبل ادعاء rollback. إلى أن يتوفر أمر ذري، تعرض النتيجة السجلات المكتوبة وخطأ التوقف وتوصية الاسترجاع المناسبة.
- **قبل العمليات الاستبدالية عالية المخاطر:** يمكن اقتراح snapshot أو backup موجّه، لكن لا يُنفذ تلقائيًا في هذه الخطة ولا يخلط مع واجهة النسخ الاحتياطي العامة.

### 12.3 استراتيجية مستقبلية اختيارية

إن احتاج كل نوع ذرية أقوى، يضاف IPC واحد لكل عملية مركبة ينفذ transaction داخل main process. لا تُنشأ transaction موزعة عامة تجمع كل أنواع الاستيراد؛ ذلك يزيد التعقيد ويصعب الاسترجاع.

## 13. الأخطاء وإعادة المحاولة

- الخطأ يظهر داخل صف/بطاقة الملف، مع ملخص قصير وتفاصيل قابلة للتوسيع.
- الخطأ يحدد المرحلة: قراءة، تصنيف، Preflight، اعتماد، أو كتابة.
- توفر إجراءات: «إعادة التحليل»، «تغيير النوع»، «تغيير السنة»، «تخطي»، و«إعادة المحاولة» بحسب الحالة.
- إعادة المحاولة تعيد الملف الفاشل فقط وتعيد تقييم الملفات التابعة له.
- لا يعاد تنفيذ ملف `succeeded` تلقائيًا.
- زر التنفيذ يصبح `disabled` و`aria-busy="true"` أثناء العمل لمنع الإرسال المكرر.
- تقدم العمليات التي تتجاوز 300ms يظهر بمؤشر واضح.
- الأخطاء العاجلة تستخدم `role="alert"`، وتحديثات التقدم تستخدم `aria-live="polite"` دون إغراق قارئ الشاشة.
- لا تستخدم الرسائل العامة مثل «حدث خطأ» وحدها؛ تذكر الملف والمرحلة والإجراء الممكن.

## 14. تقرير الجلسة

بعد التنفيذ تعرض الواجهة:

- عدد الملفات: ناجح، فاشل، متخطى، ومحجوب بسبب اعتماد.
- عدد السجلات المكتوبة/المرفوضة لكل ملف عندما يوفر المستورد هذه البيانات.
- التحذيرات قبل وبعد الاستيراد.
- أسماء غير محلولة أو سجلات تحتاج مراجعة.
- السنة والدورة والنوع النهائي لكل ملف.
- توقيت البداية والنهاية.
- إجراءات: إعادة محاولة الفاشل، فتح التحذيرات، بدء جلسة جديدة.

في المرحلة الأولى التقرير موجود داخل الذاكرة ويمكن تسجيل ملخص عبر `logImport`/`window.api.systemLogs.add`. تصدير JSON/CSV أو حفظ التفاصيل الكاملة ميزة لاحقة اختيارية وليست متطلبًا أوليًا.

## 15. تقسيم الوحدات المقترح

> كل مسار موسوم «جديد مقترح» غير موجود حاليًا ويحتاج إنشاء أثناء التنفيذ.

### 15.1 ملفات تبقى وتُعدل

| المسار الحالي | التغيير المخطط |
|---|---|
| `settings-imports.html` | إعادة بناء هيكل المركز، إضافة الطابور والمراجعة والملخص، والإبقاء على البطاقات اليدوية داخل قسم قابل للطي |
| `js/pages/settings-imports.js` | تحويله تدريجيًا إلى bootstrap/controller رقيق، مع إبقاء adapters المؤقتة أثناء الانتقال |
| `js/data-source-registry.js` | الاستمرار كسجل جاهزية المصادر؛ لا تحويله إلى Job store |
| `js/cross-source-validator.js` | الحفاظ على التحقق اللاحق واستخراج قواعد مشتركة تدريجيًا عند الحاجة |
| `js/name-resolver.js` | إعادة الاستخدام في تحليل الأسماء والتعارضات |
| `css/tailwind-input.css` | إضافة مكونات حالات الطابور والمراحل والاستجابة والوضعين |
| `css/tailwind-output.css` | يعاد توليده عبر أمر البناء المعتمد؛ لا يعدل يدويًا |
| `preload.js` و`main/ipc/*` | تعديلات فقط إذا احتاج Adapter عملية كتابة ذرية أو API غير موجودة |

### 15.2 ملفات جديدة مقترحة

```text
js/import-center/
├── import-session.js          # ImportSession + transitions
├── import-classifier.js       # pipeline وscoring
├── import-orchestrator.js     # DAG والتنفيذ وإعادة المحاولة
├── import-center-view.js      # rendering + event delegation + a11y
├── import-query-context.js    # قراءة type/year/source
└── adapters/
    ├── students-import-adapter.js
    ├── grades-import-adapter.js
    ├── absences-import-adapter.js
    ├── fet-import-adapter.js
    ├── agent-xml-import-adapter.js
    └── student-status-import-adapter.js
```

تقسيم Adapters يتم تدريجيًا. أول نسخة يمكن أن تغلف الدوال الموجودة بدل نقل جميع تفاصيلها فورًا. `js/shared/fet-import.js` الموجود يُراجع ويعاد استخدامه في FET بدل إنشاء parser مكرر.

### 15.3 حدود المسؤوليات

- **Classifier:** لا يعرف DOM ولا يكتب البيانات.
- **Adapter.analyze:** يقرأ ويحول ويجهز Preflight، بلا كتابة.
- **Adapter.execute:** ينفذ نوعًا واحدًا ويعيد عقد نتيجة موحدًا.
- **Orchestrator:** يدير الحالة والاعتماد والترتيب والإلغاء المنطقي.
- **View:** تعرض الحالة وترسل intents فقط.
- **Controller/Bootstrap:** يربط DOM والوحدات وواجهات التطبيق الحالية.

## 16. الاستمرارية والتخزين

### المرحلة الأولى: جلسة داخل الذاكرة

- `ImportSession` موجودة في ذاكرة renderer فقط.
- `File` objects لا تحفظ في `localStorage`.
- تحديث الصفحة يلغي الجلسة غير المنفذة مع تحذير قبل المغادرة إذا كانت هناك عملية جارية.
- تستمر `DataSourceRegistry` في تسجيل جاهزية المصادر الناجحة فقط.
- يستمر System Logs في تسجيل ملخص العملية.

هذا الخيار الأقل مخاطرة ولا يحتاج migrations أو IPC جديدًا لمجرد واجهة الطابور.

### المرحلة الثانية: Jobs دائمة عند إثبات الحاجة

لا تضاف إلا إذا ظهر احتياج واضح لاستئناف جلسات طويلة بعد إغلاق التطبيق أو للتدقيق التفصيلي. عندها تُصمم **مقترحًا** جداول مثل jobs/files/events بعد مراجعة قواعد الاحتفاظ والخصوصية. لا تحفظ محتويات الملفات الخام بلا ضرورة، ولا تستخدم أسماء الجداول المقترحة كأنها موجودة حاليًا.

## 17. خطة التنفيذ المرحلية

### الحزمة 0 — عينات وعقود قبول

- جمع عينات من كل نوع، تتضمن أسماء صحيحة وعامة وملفات ناقصة وملفات سنوات مختلفة.
- توثيق signatures الفعلية لكل نوع: الأوراق، العناوين، XML roots، والقيم المميزة.
- توثيق عقد نتيجة موحد دون تغيير الكتابة.
- تحديد ملفات fixture غير حساسة للاختبار المستقبلي.

**بوابة الخروج:** جدول signatures مع عينتين صحيحتين وحالات فشل لكل نوع.

### الحزمة 1 — هيكل الواجهة الجديد دون تغيير التنفيذ

- إعادة ترتيب `settings-imports.html` وفق الأقسام المستهدفة.
- إضافة Drop Zone متعدد الملفات وطابور ثابت ببيانات تجريبية/حالة داخل الذاكرة.
- نقل البطاقات الحالية إلى Accordion مع الحفاظ على handlers الحالية.
- فصل النسخ الاحتياطي وإدارة البيانات.
- إضافة حالات focus/hover/disabled/loading والوصول.

**بوابة الخروج:** جميع الاستيرادات اليدوية الحالية تعمل كما كانت، والواجهة تعمل على RTL وشاشة ضيقة.

### الحزمة 2 — نموذج الجلسة والمصنف

- إنشاء `import-session.js` و`import-classifier.js`.
- تحليل كل ملف منفردًا.
- إعادة استخدام `inferImportActionFromFiles` فقط كإشارة legacy منخفضة الوزن، لا كقرار نهائي.
- عرض evidence والثقة والبدائل.
- دعم تعديل النوع وإعادة التحليل.

**بوابة الخروج:** دفعة مختلطة تُصنف إلى عناصر مستقلة دون كتابة بيانات.

### الحزمة 3 — Adapters وPreflight

- تعريف عقد `analyze/execute`.
- بدءًا بالتلاميذ والنقط، ثم الغياب، ثم XML وFET والوضعية.
- استخراج القراءة والتحويل من `js/pages/settings-imports.js` تدريجيًا.
- دمج كشف السنة والتحقق من الاختلاف.
- توصيل NameResolver والقواعد العابرة للمصادر حيث تنطبق.

**بوابة الخروج:** كل نوع ينتج Preflight ومعاينة دون كتابة، والاستيراد اليدوي لم ينكسر.

### الحزمة 4 — Orchestrator والاعتمادات

- إنشاء DAG من Preflight.
- تنفيذ تسلسلي وفق topological order.
- منع الملفات التابعة عند الفشل.
- تقدم عام ولكل ملف، إلغاء بدء ملفات جديدة، وإعادة محاولة ملف واحد.
- منع النقر المكرر وتجميد التعديلات أثناء كتابة الملف.

**بوابة الخروج:** دفعة مختلطة تنفذ بالترتيب وتنتج نجاحًا جزئيًا واضحًا عند فشل أحد الملفات.

### الحزمة 5 — الذرية والسلامة

- جرد أوامر IPC لكل Adapter.
- توثيق العمليات الاستبدالية والإلحاقية.
- إضافة IPC transactions محددة فقط حيث توجد فجوة مثبتة، خصوصًا استبدال الغياب إن لم يكن ذريًا.
- إضافة fingerprint وتحذير التكرار داخل الجلسة إذا كانت العينات تسمح.

**بوابة الخروج:** لا توجد عملية استبدال يمكن أن تنتهي بعد الحذف وقبل الحفظ دون معالجة أو توثيق صريح.

### الحزمة 6 — الاختصارات السياقية والتقرير

- إضافة روابط صفحات المجالات إلى `settings-imports.html?type=...`.
- قراءة Query Parameters وتطبيقها كتلميح فقط.
- إضافة ملخص الجلسة والسجل المختصر.
- توصيل تحديث `DataSourceRegistry` والتحقق اللاحق الحاليين.

**بوابة الخروج:** كل اختصار يفتح المركز في السياق الصحيح ولا ينفذ تلقائيًا.

### الحزمة 7 — التنظيف التدريجي

- إزالة المسارات المكررة فقط بعد ثبوت استخدام Adapters.
- الإبقاء مؤقتًا على wrappers متوافقة للأسماء القديمة إن كانت HTML أو أحداث أخرى تستدعيها.
- تحديث الوثائق وتعليقات العقود.
- تقييم الحاجة إلى Jobs دائمة؛ الافتراضي رفضها ما لم توجد حالة استخدام مثبتة.

## 18. السلامة أثناء الترحيل

- كل حزمة قابلة للرجوع دون migration غير ضروري.
- لا يزال القسم اليدوي متاحًا حتى اجتياز المصنف وAdapters معايير القبول.
- يستخدم Feature Flag محلي مؤقت إذا لزم طرح المركز الذكي تدريجيًا.
- لا تُحذف `runImport` أو `handleImport` قبل نقل جميع المستدعين أو توفير wrappers.
- أي IPC كتابة جديد يتبع نمط التفويض والتسجيل الموجود في المشروع ويسجل في `main/ipc/registerAll.js` ويُعرض عبر `preload.js` عند الحاجة.
- لا تُعدل قاعدة البيانات لمجرد حفظ حالة واجهة مؤقتة.

## 19. الوصول والتصميم البصري

- الصفحة RTL أولًا مع ترتيب قراءة DOM منطقي، لا انعكاس بصري فقط.
- Drop Zone يستخدم زر ملف حقيقي قابلًا للوحة المفاتيح، ولا يعتمد على السحب وحده.
- الحد الأدنى للأهداف التفاعلية 44×44px.
- جميع الأزرار الأيقونية لها تسمية نصية أو `aria-label`، وتستخدم عائلة أيقونات متجهية واحدة بدل Emoji.
- الحالات لا تعتمد على اللون وحده: أيقونة + نص + لون.
- تباين النص العادي لا يقل عن 4.5:1، والعناصر الكبيرة/المكونات لا يقل عن 3:1.
- تركيز لوحة المفاتيح ظاهر بوضوح، مع Skip Link إلى المحتوى الرئيسي عند الحاجة.
- التقدم يستخدم `aria-live="polite"`، والأخطاء المرتبطة بالإجراء تستخدم `role="alert"`.
- الحركة الدقيقة 150–300ms، مع `prefers-reduced-motion` لإيقاف الحركات غير الضرورية.
- لا تستخدم animation مستمرة إلا لمؤشر تحميل فعلي.
- يستخدم المشروع tokens القائمة للوضعين الفاتح والداكن؛ لا تنسخ ألوان مخرجات أداة التصميم حرفيًا.
- تستخدم طبقات z-index محددة، لا قيمًا عشوائية كبيرة.
- في 375px والاتجاه الأفقي تبقى الإجراءات الأساسية مرئية ولا يختفي المحتوى خلف عناصر ثابتة.

## 20. معايير القبول

### التصنيف والمراجعة

- يستطيع المستخدم اختيار أو إسقاط ملفات متعددة من أنواع مختلفة دفعة واحدة.
- يظهر عنصر مستقل لكل ملف، ولا يفرض نوع ملف واحد على الدفعة.
- يعرض كل عنصر النوع والثقة والدليل والسنة/الدورة والحالة.
- أي ملف منخفض الثقة أو ملتبس لا يصبح جاهزًا قبل تدخل المستخدم.
- لا تتم كتابة أي بيانات أثناء التحليل أو Preflight.

### الاعتماد والتنفيذ

- يحدد النظام اعتماد كل ملف ويشرح سبب الانتظار.
- يبدأ التنفيذ بعد تأكيد صريح فقط.
- يمنع زر التنفيذ أثناء العمل ويعرض تقدمًا واضحًا.
- فشل ملف يوقف الملفات التابعة فقط، ولا يعيد تلقائيًا الملفات الناجحة.
- يمكن إعادة محاولة ملف فاشل منفردًا.

### السلامة

- اختلاف السنة يظهر كتحذير/خطأ وفق سياسة النوع ولا يُتجاهل بصمت.
- كل عملية استبدال بيانات موثقة من حيث الذرية والاسترجاع.
- يبقى مسار الغياب staged، ولا يُضعف أثناء إعادة الهيكلة.
- لا تُضاف جداول Jobs في المرحلة الأولى.

### التوافق

- بطاقات الاستيراد اليدوي الحالية تبقى قابلة للاستخدام أثناء الانتقال.
- `DataSourceRegistry` يستمر في تمثيل جاهزية المصادر، لا الجلسات.
- `CrossSourceValidator` يستمر في التحقق اللاحق بعقده الحالي.
- النسخ الاحتياطي والاستعادة يبقيان منفصلين عن الاستيراد التشغيلي.

### الواجهة والوصول

- الواجهة قابلة للاستخدام بلوحة المفاتيح وبقارئ الشاشة.
- الأخطاء قريبة من الملف المسبب لها.
- الحالة مفهومة دون الاعتماد على اللون وحده.
- الوضعان الفاتح والداكن وتفضيل تقليل الحركة مدعومة.
- التخطيط يعمل على 375px، والأجهزة الكبيرة، والاتجاه الأفقي.

## 21. سيناريوهات التحقق المستقبلية

> هذه سيناريوهات قبول للتنفيذ اللاحق، وليست اختبارات أضيفت ضمن هذه الوثيقة.

1. **دفعة صحيحة مختلطة:** تلاميذ + نقط + غياب + FET؛ تصنيف مستقل، ترتيب اعتماد صحيح، وملخص نجاح.
2. **أسماء ملفات عامة:** `file1.xlsx` و`data.xlsx`؛ ينجح التصنيف من headers لا الاسم.
3. **XML ملتبس:** root غير معروف؛ يحتاج اختيارًا يدويًا ولا يكتب.
4. **سنتان مختلفتان:** ملف تلاميذ للسنة النشطة وملف غياب لسنة أخرى؛ يظهر التعارض قبل التأكيد.
5. **ملف تالف:** يفشل التحليل لهذا الملف فقط مع رسالة وإعادة محاولة.
6. **اعتماد فاشل:** يفشل ملف التلاميذ؛ تُحجب النقط التابعة مع سبب واضح.
7. **نجاح جزئي:** ينجح FET ويفشل الغياب؛ لا يعاد FET عند إعادة محاولة الغياب.
8. **تغيير النوع يدويًا:** يختار المستخدم «نقط» لملف منخفض الثقة؛ يعاد Preflight قبل الجاهزية.
9. **نقر مزدوج:** لا تبدأ عمليتان متوازيتان لنفس الجلسة.
10. **لوحة المفاتيح:** اختيار الملفات، مراجعة النوع، بدء التنفيذ، فتح الخطأ وإعادة المحاولة دون فأرة.
11. **قارئ الشاشة:** يعلن الانتقال للحالة والأخطاء المهمة دون تكرار مفرط.
12. **الوضع الداكن/التباين:** الحالات والحدود والتركيز واضحة في الوضعين.
13. **تقليل الحركة:** لا توجد حركة زخرفية مستمرة، ويبقى التقدم مفهومًا.
14. **اختصار سياقي:** رابط `?type=grades` يجهز السياق ولا يتجاوز التصنيف أو التأكيد.
15. **Regression يدوي:** كل بطاقة استيراد حالية تستمر في تشغيل مسارها السابق أثناء الحزم الانتقالية.

بعد التنفيذ تشغّل أوامر المشروع الملائمة: `npm test` و`npm run lint`، إضافة إلى سيناريوهات Electron اليدوية التي تتطلب اختيار ملفات حقيقية.

## 22. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| تشابه قوالب Excel | signatures متعددة + evidence + threshold + fallback يدوي |
| استهلاك الذاكرة مع ملفات كبيرة | قراءة metadata/عينات أولًا، معالجة متسلسلة، وعدم الاحتفاظ بنسخ parsed غير لازمة |
| اختلاف القوالب بين السنوات | classifier versioned signatures وعينات قبول لكل قالب |
| كسر المستوردات الحالية أثناء التقسيم | wrappers وAdapters تدريجية والإبقاء على المسار اليدوي |
| نجاح جزئي غير مفهوم | ملخص ملفي، DAG مرئي، ومنع الملفات التابعة |
| حذف ثم فشل حفظ | جرد العمليات الاستبدالية وإضافة transaction IPC محدد عند الحاجة |
| تكرار الاستيراد | fingerprint وتحذير داخل الجلسة أولًا، وحماية أقوى لاحقًا إذا ثبت الاحتياج |
| ضوضاء قارئ الشاشة | live region للتقدم المجمل، وalerts انتقائية للأخطاء القابلة للتصرف |
| تضخم نطاق المشروع | in-memory أولًا، رفض durable jobs والتوازي والتصدير حتى تثبت الحاجة |

## 23. تعريف الإنجاز

تعد الميزة منجزة عندما:

- يعمل مركز واحد بمدخل ذكي متعدد الملفات ويصنف كل ملف بناءً على المحتوى.
- يراجع المستخدم النوع والسنة والتحذيرات قبل أي كتابة.
- تُنفذ الملفات بترتيب اعتماد واضح وتظهر نتيجة مستقلة لكل ملف.
- يمكن معالجة الفشل وإعادة المحاولة دون إعادة الملفات الناجحة.
- تظل المسارات اليدوية الحالية متاحة ومتوافقة خلال الانتقال.
- تكون عمليات الاستبدال عالية المخاطر ذرية أو موثقة بحدودها وإجراء استرجاع واضح.
- تعمل الواجهة RTL على أحجام الشاشة المستهدفة وفي الوضعين ومع تقليل الحركة.
- تمر أوامر `npm test` و`npm run lint` بعد التنفيذ، وتنجح سيناريوهات القبول الأساسية بملفات fixtures معتمدة.
- تُحدّث الوثائق لتوضح الوحدات الجديدة وحدود DataSourceRegistry وCrossSourceValidator وسجل النظام.

## 24. ترتيب البدء الموصى به

ابدأ بالحزم 0 و1 و2 فقط: العينات والعقود، هيكل الواجهة، ثم التصنيف دون كتابة. هذه البداية تحقق أعلى قيمة مرئية وتختبر أصعب فرضية — القدرة على التعرف الموثوق على الملفات — من دون تعريض بيانات المستخدم للخطر. بعد معايرة المصنف على ملفات حقيقية، انتقل إلى Preflight وAdapters، ثم Orchestrator والذرية.
